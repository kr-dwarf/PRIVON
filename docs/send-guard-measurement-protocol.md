# Send Guard Measurement Protocol (A-1)

이 문서는 [Send Guard Proof Contract](send-guard-proof-contract.md)의 합격 조건을 측정하기 위한 **절차 초안**이다.

- **이 문서는 실행되지 않았다.** 실제 클립보드, 키보드, 마우스 실험, OS 후킹, 외부 앱 입력, 실제 Send 클릭은 Controller의 별도 승인 전에는 실행하지 않는다.
- 이 문서에 적힌 수치 기준은 제안이며, Controller가 확정한다.
- **비출고 연구 자료**이다. 출고 앱과 릴리스 패키지에 포함되지 않으며, 이 절차나 관련 실험은 전송 차단이 구현되었거나 검증되었다는 뜻이 아니다. A-1은 열린 상태이다.
- 어떤 측정 결과도 제품 보안 기능의 근거로 쓰기 전에 계약의 G1~G4와 대조한다.

## 1. 사전 조건

| 항목 | 요구 |
|---|---|
| 실행 환경 | 사용자의 일상 세션과 **분리된 환경**: 전용 Windows VM, 또는 전용 사용자 세션. 클립보드와 전경 창은 세션 전체에서 공유되므로, 일상 작업 중인 세션에서는 실행하지 않는다 |
| 네트워크 | X0는 **오프라인**(어댑터 비활성 또는 방화벽 차단). 격리 테스트 대상 앱에는 네트워크 코드가 없어야 한다 |
| 데이터 | **합성 문자열만** 사용한다. 실제 개인정보, 실제 계정 정보 금지 |
| 저장 폴더 | 실험 전용 폴더 `%TEMP%\PRIVON-A1\run-<id>\`. 사용자의 실제 PRIVON 저장소(`%LocalAppData%\PRIVON`)와 완전히 분리한다 |
| 사용자의 클립보드 | 실험 전에 사용자의 실제 클립보드에 중요한 내용이 없음을 확인한다. 전용 세션을 쓰면 해당 없음 |
| 실행 이력 | 실험 실행 전 Controller 승인 기록(날짜, 범위, 단계)을 실행 폴더에 남긴다 |

## 2. 합성 데이터 규칙

- 원문 PII 형태는 이 저장소의 테스트가 이미 쓰는 **명백히 가짜인 값**만 쓴다 (예: `SSN: 321-54-9876`, `010-1234-5678`, `user@example.test`).
- 시도마다 **카나리 토큰**을 덧붙여 식별한다: `CANARY-<runId>-<trialId>`. 카나리는 PII처럼 보이지 않는 임의 문자열이다.
- 내용 종류(`ContentClass`)를 세 가지로 구분한다: `raw`(원문 PII 포함), `protected`(PRIVON이 재작성한 값), `clean`(PII 없음).
- 로그, 파일, 화면 캡처에 **원문을 남기지 않는다.** 기록은 `ContentClass`, 길이, 실행별 솔트 해시, 카나리 토큰만 허용한다.

## 3. 격리 테스트 대상(X0)의 요구사항

(제작은 Controller 승인 후. 제품 어셈블리나 기존 스파이크 코드를 수정하지 않는다.)

- 텍스트 입력 상자 하나와 `Send` 버튼 하나. 전송 단축키는 설정 가능(Enter, Ctrl+Enter).
- 전송 이벤트는 **로컬 수신기**에만 기록한다: `{ trialId, timestampUtc, contentClass, length, salted_hash }`. 원문은 기록하지 않는다.
- UIA 제공자를 **켜고 끌 수 있는 스위치**를 제공한다. 이것으로 UIA 실패를 결정적으로 주입한다 (외부 앱의 UIA를 건드리지 않는다).
- Send 버튼 위치를 바꾸는 스위치를 제공한다: 창 이동, 크기 변경, 컴포저 줄 증가, DPI 변경.
- 숫자패드 Enter, 키보드 포커스 활성화, `InvokePattern` 호출을 각각 수신기에서 구분해 기록한다.
- 네트워크 코드를 포함하지 않는다.

## 4. 측정 항목

모든 시도는 아래 한 행으로 기록한다.

| 필드 | 설명 |
|---|---|
| `runId`, `trialId` | 실행, 시도 식별자 |
| `route` | R1~R5 |
| `condition` | 아래 5절의 조건 이름 |
| `contentClass` | raw / protected / clean |
| `guardStateAtIntent` | 입력 순간의 통제 상태 (ARMED / UNARMED / UNCERTAIN / OUT_OF_SCOPE) |
| `outcome` | `blocked` / `sent` / `held` / `forwarded` |
| `sentAtUtc`, `intentAtUtc` | 수신기 전송 시각, 입력 시각 |
| `latencyMs` | 입력에서 판정까지 |
| `leak` | `contentClass==raw` 이고 `outcome==sent` |
| `falseBlock` | `contentClass in {protected, clean}` 이고 `outcome!=sent` |
| `duplicate`, `altered` | 중복 전송, 수신 내용이 기대와 다른 경우 |

**집계**: 경로 × 조건별 (n, leak, falseBlock, duplicate, altered, 평균/p95/최대 latency, `UNCERTAIN` 지속 시간 분포).

## 5. 시험 조건 매트릭스

각 경로(R1~R5)에 대해 다음 조건을 모두 실행한다. 셀마다 n≥300 (기능 확인 단계).

| 조건 | 설명 | 연결 |
|---|---|---|
| C0 정상 | 대상 식별 정상, 통제 정상 | G2-1 |
| C1 UIA 실패 | 테스트 대상의 UIA 제공자를 끄거나 지연시킨다. **실패 중에 전송을 시도**한다 | G1-4, G4 |
| C2 창 이동 | 전송 시도와 동시에 창을 이동한다 | G1-3 |
| C3 크기·줄 증가 | 컴포저를 늘려 Send 위치를 바꾼 직후 전송을 시도한다 | G1-3 |
| C4 전경 전환 | 다른 앱(테스트용 메모 창)으로 전환 후 복귀, 전환 직후 입력 | G4, 타 앱 입력 삼킴 여부 |
| C5 앱 재시작 | 대상 종료·재시작 직후 전송 시도 (PID/HWND 재사용 포함 시도) | G1-2 |
| C6 한국어 IME 조합 | 조합 중 Enter | G3-7 |
| C7 DPI·다중 모니터 | 배율 변경, 모니터 이동 | G1-3 |
| C8 정상 전송 | `protected`/`clean` 내용 전송 | G3-2 |
| C9 경쟁 | 판정 직전·직후·판정 중 임의 시점(0~500 ms)에 내용을 `raw`로 변경 | G3-3 |
| C10 내용·대상 변경 후 재사용 | 허용 판정 후 내용/epoch를 바꾸고 전송 | G3-4 |
| C11 전송 취소 | 차단·취소 후 컴포저 내용 해시 비교 | G3-6 |
| C12 키 반복 | Enter 길게 누름 | 중복 전송 방지 |
| C13 비정상 종료 | PRIVON 프로세스를 강제 종료한 뒤 입력과 창 상태 확인 | G4, 진입 조건 6 |

R5(키보드/접근성)는 PRIVON이 통제 소유자를 갖지 못할 수 있으므로, 목적은 "차단 성공"이 아니라 **누출 여부와 통제 소유자 유무를 사실로 기록하는 것**이다.

## 6. 절차

### 6.1 시작
1. Controller 승인 기록 확인 (단계, 범위, 날짜).
2. 환경 점검: 오프라인, 전용 세션/VM, 실험 폴더 생성, 사용자 클립보드 비어 있음.
3. **데드맨 타이머** 설정: 실행기가 최대 시간(제안: 10분)을 정하고, 그 시간이 지나면 가드 프로세스를 종료하고 자원 정리를 확인한다. 가드가 입력을 가로채는 실험이므로 사람이 키를 누를 수 없는 상태가 되지 않도록, 항상 별도의 **실행기 프로세스**가 감시한다.
4. 시작 전 상태 캡처: 등록된 핫키 없음, 잔존 shield 창 없음, 대상 앱 정상 입력.

### 6.2 실행
1. 조건 매트릭스를 임의 순서로 실행한다 (순서 편향 제거).
2. 각 시도 후 수신기 기록과 가드 상태 기록을 합쳐 한 행을 만든다.
3. 입력은 가능한 한 합성 입력(자동화)으로 보내되, 자동화 입력이 실제 사람 입력과 다른 경로를 타는지(예: 주입 플래그)를 별도 항목으로 기록한다. 사람 입력 표본(최소 n=30/경로)을 병행한다.

### 6.3 중단 조건
다음 중 하나라도 발생하면 즉시 중단하고 정리한다.
- 타 앱의 정상 입력이 삼켜진다.
- 입력 장치가 응답하지 않는다 (사람이 복구할 수 없는 상태 포함).
- 원문이 의도치 않은 위치(로그, 파일, 네트워크)에 기록되거나 나간 징후.
- 데드맨 타이머 만료.
- 가드가 `UNCERTAIN`을 `ARMED`로 표기한 사례 1건 (계약 위반).

### 6.4 정리 및 확인
1. 가드 프로세스 종료 (정상 종료 후 강제 종료 시험은 C13에서만).
2. 핫키 해제 확인: 대상 앱에서 Enter가 정상 동작.
3. shield 창 잔존 0 확인.
4. 실험 폴더의 원문 검색: 카나리/원문 문자열이 로그에 없는지 확인 (있으면 폴더를 안전 삭제하고 사건 기록).
5. 환경 복원: VM이면 스냅샷 복원.

### 6.5 비상 복구 (입력이 막힌 경우)
- 별도 실행기 프로세스가 가드를 강제 종료한다.
- 그것도 불가능하면 `Ctrl+Alt+Del` → 작업 관리자에서 가드와 대상 프로세스 종료, 필요하면 로그오프. 이 절차를 시작 전에 실행자가 숙지하고 기록한다.

## 7. 결과 판정

- 각 셀의 누출 0 → 95% 상한은 `3/n` (n=300에서 1.0%, n=3000에서 0.1%).
- 한 건이라도 `leak`이 있는 셀은 불합격이며, 원인(어느 조건에서, 통제 상태는 무엇이었나)을 기록한다.
- `UNCERTAIN`이 `ARMED`로 표기된 행, `UNCERTAIN` 상태에서 `sent`가 된 `raw`가 있으면 계약 위반으로 별도 보고한다.
- 판정에는 **통과한 경로의 목록**만 쓴다. 전체 요약 문장("차단됨")을 쓰지 않는다.
- 결과 보고에는 항상 한계를 적는다: 환경, 앱, 버전, 로케일, 표본 수, 자동화 입력 사용 여부.

## 8. 단계별 승인

| 단계 | 실행 가능 조건 |
|---|---|
| X0 | Controller 승인 + 격리 테스트 대상 앱 제작 승인 |
| X1 | X0 합격 + 별도 승인. 별도 계정, 합성 카나리, 외부 전송 승인, 대화 삭제 절차 |
| X2 | X1 합격 + 별도 승인 |

실험에 쓰인 전역 입력 통제(핫키 등)는 실험이 끝나면 반드시 해제되었음이 6.4에서 확인되어야 한다.
