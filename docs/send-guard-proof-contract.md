# Send Guard Proof Contract (A-1)

이 문서는 **설계·측정 계약**이다. 제품 기능이 아니며, 구현 승인이 아니다.

- 현재 제품의 지원 범위는 **Clipboard-first**이다. 이 문서는 그것을 바꾸지 않는다.
- **비출고 연구 자료**이다. 출고 앱과 릴리스 패키지에 포함되지 않으며, 이 문서와 관련 실험은 전송 차단이 구현되었거나 검증되었다는 뜻이 아니다. A-1은 열린 상태이다.
- Clipboard `Verified`는 "클립보드 재작성 후 읽기 확인"만 뜻한다. 전송이 차단되었다는 뜻도, 전송이 안전하다는 뜻도 아니다.
- 이 문서의 어떤 기준도 "통과했다"고 기록된 적이 없다. 합격 조건은 **아직 미충족**이며, 상태는 `A1_FAIL_CLOSED_PROVEN=FALSE`, `A1_FULLY_RESOLVED=FALSE`이다.
- `tools/UiaInspector`의 Phase 0 스파이크는 출고 코드로 승격하지 않는다. 이 문서가 요구하는 증거는 스파이크가 아니라 별도 검증 대상이 만들어야 한다.
- 근거 기록(Phase 0 실측)은 보존한다: https://app.notion.com/p/3bcfce3c4fde81bcba35f186a18ddc0f

## 0. 용어와 상태 모델

**전송 경로(Route)**

| ID | 경로 |
|---|---|
| R1 | Enter |
| R2 | 숫자패드 Enter |
| R3 | 앱에 설정된 다른 전송 단축키 (예: Ctrl+Enter) |
| R4 | 마우스로 Send 버튼 클릭 |
| R5 | 키보드/접근성 기반 버튼 활성화 (Tab+Space, 화면 낭독기, 음성 제어, UIA `InvokePattern` 호출) |

**경로별 통제 상태**

| 상태 | 뜻 |
|---|---|
| `ARMED` | 통제가 작동 중이고, 그 근거가 신선하며 기계적으로 확인됨 |
| `UNARMED` | 통제가 없음이 알려져 있음 (등록 실패, 생성 실패, 미지원 앱) |
| `UNCERTAIN` | 통제가 작동하는지 알 수 없음 |
| `OUT_OF_SCOPE` | 이 계약이 통제하지 않기로 한 경로 또는 대상 |

**불변 규칙**

- `UNCERTAIN`은 `ARMED`로 취급하지 않는다. 사용자 표시, 로그, 주장 어디에서도 마찬가지다.
- 보호 주장은 **증명된 `ARMED` 경로의 집합**에서 기계적으로 도출한다. "모든 전송 차단"과 "전송 안전"이라는 문구는 도출 대상이 아니며 쓰지 않는다.
- 하나의 경로가 통과했다고 전체 통과로 판정하지 않는다. 각 경로는 G1~G4를 독립적으로 통과해야 한다.
- 이 계약에서 "fail-closed"는 **불확실하거나 실패한 상태에서 미보호 원문이 전송되지 않는 것**을 뜻한다. 현재 코드베이스의 "fail-closed"(개입하지 않고 주장하지 않음)와 다른 뜻이므로 혼동하지 않는다.

## 2. G1 — 대상 식별

**질문**: 지원 앱의 올바른 컴포저와 Send 영역을 식별할 수 있는가?

**대상 식별 기준(Target Epoch)**: 다음을 모두 묶은 값이며, 하나라도 달라지면 새 epoch이다.

- 프로세스: PID와 **프로세스 시작 시각**, 그리고 제품의 `TargetGate` 판정(PFN 또는 서명 조직). 소스에는 `RetainedProcess`/`RetainedProcessLiveness`가 있으나 재사용 가능 여부는 이 계약에서 검토하지 않았다.
- 최상위 창 HWND와 그 창의 현재 생존 여부
- 컴포저 요소의 UIA `RuntimeId`와 포커스 상태
- Send 영역: 마지막 성공 탐색 시각, 창 좌표, 창 크기, DPI

**합격 조건**

| ID | 조건 |
|---|---|
| G1-1 | 올바른 컴포저와 Send 영역을 식별한다. 잘못된 대상을 맞다고 판정(false accept)한 횟수는 **0** (n≥300) |
| G1-2 | 이전 epoch의 HWND, 좌표, `RuntimeId`를 현재 대상으로 재사용하지 않는다. 앱 재시작, 창 닫고 열기, 새 대화, 탭 전환, 같은 PID/HWND 재사용을 유도한 시험에서 재사용 **0** |
| G1-3 | 창 이동, 크기 변경, DPI 변경, 다중 모니터 이동 후 Send 영역 식별이 유효하거나, 유효성을 잃었음을 감지해 `UNCERTAIN`으로 전이한다. 감지 지연의 상한과 분포를 기록한다 |
| G1-4 | UIA 탐색 실패 중에도 **UIA에 의존하지 않는 통제**가 무엇인지 명시하고, 그 통제가 실제로 유지됨을 보인다 (아래 참고) |
| G1-5 | 대상이 사라지거나 미지원 앱으로 전환되면 통제가 해제된다 (G4와 연동) |

**UIA 실패 중 유지되어야 하는 통제의 후보**

- 핫키 등록의 근거를 UIA 포커스 판정이 아니라 **전경 창의 기계적 사실**(PID, PFN 또는 서명)로 둔다. 컴포저인지 여부는 키 입력 시점에 판정한다.
- 마우스 shield의 위치 근거를 UIA 직접 탐색이 아니라 **창 상대 좌표 캐시**로 둔다. 단, 컴포저가 여러 줄로 늘어나는 등 레이아웃이 바뀌면 캐시가 무효가 되는지를 실측해야 한다. 무효가 감지되지 않는다면 이 후보는 불합격이다.

**불합격 조건**: false accept 1건 이상, 또는 이전 epoch 값을 현재로 오인한 사례 1건 이상.

## 3. G2 — 실제 전송 차단

**소유자와 증명 방법은 경로마다 따로 정한다.** 한 경로의 성공은 다른 경로에 영향을 주지 않는다.

| 경로 | 차단 소유자 (후보) | 증명 방법 | 비고 |
|---|---|---|---|
| R1 Enter | 소유 스레드의 `RegisterHotKey(VK_RETURN)` | 격리된 수신기에서 원문 전송 0 | Phase 0 PASS 범위: ChatGPT, 포커스 판정 성공 시 |
| R2 숫자패드 Enter | `RegisterHotKey`가 숫자패드 Enter를 같은 `VK_RETURN`으로 받는지는 **미확인** | 실제 숫자패드(또는 확장 키 플래그) 입력으로 차단 여부를 별도 측정 | UNPROVEN |
| R3 설정 단축키 | 앱 설정에서 현재 전송 단축키를 **알아내는 방법 자체가 없음** | (a) 앱 설정을 읽는 방법을 입증, 또는 (b) 가능한 모든 단축키를 등록해도 정상 입력이 깨지지 않음을 입증 | 후보 (b)는 Ctrl+Enter의 줄바꿈 용도를 삼킬 위험 |
| R4 마우스 클릭 | 네이티브 shield 창 | 클릭 누출 0 (이동, 크기 변경, UIA 실패 조건 포함) | Phase 0 누출 2건 발생 경로 |
| R5 키보드/접근성 활성화 | **PRIVON이 소유할 통제 지점이 존재하지 않음** (키보드로 버튼에 포커스가 있을 때의 Space/Enter, 접근성 클라이언트의 `InvokePattern`은 앱의 제공자로 직접 전달됨) | 차단 시도 없음. 아래 "R5 처리 규칙" | 구조적 한계 |

**R5 처리 규칙**: R5에 소유자가 없다면, 어떤 Send Guard도 "모든 전송 경로를 차단한다"는 주장을 할 수 없다. 이 경우 제품 문구는 **차단하는 경로를 열거하고 나머지를 미보호로 명시**하는 경로 한정 형태로만 허용되며, 그 문구 승인은 Controller의 몫이다. R5가 포커스 이동을 통해 Enter 경로로 합쳐지는지(버튼에 포커스가 있을 때 Enter가 R1 핫키로 잡히는지)는 실측 항목이다.

**합격 조건**

| ID | 조건 |
|---|---|
| G2-1 | 경로별로 (조건 × 시도 횟수 × 누출 횟수)를 기록한다. 시도 횟수는 경로·조건마다 **n≥300**, 누출 **0** (95% 상한 약 1%). 제품 게이트로 가려면 n≥3000 (상한 약 0.1%)을 Controller가 별도로 정한다 |
| G2-2 | 조건에는 정상 상태 외에 UIA 실패 주입, 창 이동/크기 변경 중, 전경 전환 직후, 앱 재시작 직후, 한국어 IME 조합 중을 반드시 포함한다 |
| G2-3 | 차단이 **전송 전에** 작동함을 격리된 수신기의 전송 타임스탬프로 보인다 (차단 신호가 전송보다 늦으면 불합격) |
| G2-4 | 모든 경로에서 "통제 소유자 없음"인 경로는 `OUT_OF_SCOPE`/`UNARMED`로 기록하고, 해당 사실이 주장 문구에 반영됨을 보인다 |
| G2-5 | 경로 일부만 통과한 경우, 통과 경로 목록만으로 주장이 도출되고 나머지는 미보호로 표시된다 |

**불합격 조건**: 어떤 경로든 정당한 시도에서 누출 1건 이상이면 그 경로는 불합격이다. 그 경로를 주장 목록에서 제외하지 않고 "차단"으로 표기하는 것은 계약 위반이다.

## 4. G3 — 안전한 정상 전송 (가장 중요한 조건)

**원칙**: 미보호 원문은 전송되지 않고, 보호 완료된 텍스트는 정상 전송된다. 이 둘을 동시에 만족하는 구조가 없으면 보안 기능 구현을 진행하지 않는다.

**합격 조건**

| ID | 조건 |
|---|---|
| G3-1 | 원문이 있는 컴포저에서 전송 시도 n≥300, 전송 **0** |
| G3-2 | 보호 완료 텍스트 또는 PII 없음으로 판정된 텍스트의 전송 시도 n≥300에서 정상 전송률 ≥99%, **중복 전송 0, 개행 삽입 0, 내용 훼손 0** (수신기에서 바이트 비교) |
| G3-3 | **검증과 해제 사이 경쟁**: 판정 직전, 직후, 판정 중 임의 시점(0~500 ms)에 컴포저 내용을 원문으로 바꾸는 시험 n≥300에서 원문 전송 **0**. 경쟁 구간의 최대 크기를 측정해 기록한다 |
| G3-4 | **허용 결정 재사용 금지**: 허용 판정 후 내용, 대상 epoch, 전경 앱 중 하나가 바뀐 모든 시험에서 이전 결정 재사용 **0** |
| G3-5 | **무조건 해제 금지**: 핫키 해제와 shield 숨김이 어떤 코드 경로에서도 "정상 전송을 위한 일반 수단"으로 쓰이지 않는다. UIA 실패를 강제한 상태에서 통제가 해제되지 않는다 (코드 검토와 실측 모두) |
| G3-6 | **전송 취소**: 차단되거나 취소된 시도 후 컴포저의 내용이 바이트 단위로 동일하다. 임의 삭제 **0**, PRIVON이 컴포저에 쓰지 않는다 |
| G3-7 | **삼켜진 입력**: 차단된 Enter가 입력 흐름에 부작용(IME 조합 손상, 키 반복에 의한 다중 처리)을 일으키지 않는다 |

**구조 후보** (모두 입증 전이며, 현재 G3에 대한 구조적 해결책은 **없다**)

| 후보 | 개념 | 핵심 위험 |
|---|---|---|
| S1 입력 시점 판정 | 핫키가 항상 무장된 상태에서, 키가 눌린 **그 순간** 컴포저를 새로 읽어 판정한다. 깨끗하면 해당 입력을 앱으로 전달하고, 읽기 실패이거나 원문이면 보류한다. 저장된 허용 상태가 없으므로 G3-4가 구조적으로 성립한다 | (1) 전달 수단. 단일 Enter의 재주입(`SendInput`)은 Phase 0이 컴포저 쓰기에 대해 불가 판정한 기법과 같은 계열이며, 단일 키 전달에 대해서는 미측정이다. (2) 읽기와 전달 사이의 경쟁(G3-3). (3) 판정 읽기 지연이 UIA 공백과 같은 분포이면 정상 전송이 자주 보류되어 사용 불가가 됨 |
| S2 허용 토큰 | 판정이 깨끗하면 내용 해시와 epoch에 묶인 짧은 허용을 발급하고, 허용 동안 통제를 푼다. 내용이 바뀌면 재무장한다 | 재무장이 컴포저 변경 이벤트(UIA)에 의존한다. 이벤트 지연이나 누락 동안 사용자가 원문을 입력한 뒤 바로 전송하면 누출. 키 입력을 직접 관찰할 수 없으므로(후킹 불가) 이 경쟁을 구조적으로 닫지 못한다 |
| S3 차단 전용 | 통제를 풀지 않고 항상 막는다 | 정상 전송 불가. G3-2 불합격. **기각** |

**중요 제약 (Controller 결정 필요)**: S1은 PRIVON이 사용자의 입력을 앱에 전달하는 구조다. README의 "PRIVON never sends anything on your behalf"와 충돌하는지 검토해야 한다. 마우스 경로에서 정상 클릭을 허용하려면 shield를 통과해 클릭을 앱에 전달하거나, UIA `InvokePattern`으로 PRIVON이 버튼을 호출해야 하며, 후자는 문자 그대로 PRIVON이 전송을 수행하는 것이다.

**G3 판정**: 위 합격 조건 중 하나라도 증거가 없으면 `G3=FALSE`이고, 구현 진입은 막힌다.

## 5. G4 — 실패 시 행동

각 상황에서 일어나는 일은 아래 넷 중 하나다: 차단 유지 / 전송 허용 / 보호 범위 이탈 및 경고 / 상태 불확실. **상태 불확실은 보호 완료가 아니다.** 표는 증명해야 할 **정책**이며, 구현된 동작이 아니다.

| 상황 | R1~R3 (키보드) | R4 (마우스) | 상태 분류 | 사용자 경고 | 입증 방법 |
|---|---|---|---|---|---|
| UIA 탐색 실패 | 핫키는 전경 창 사실에 근거해 유지. 입력 시점 판정이 읽기 실패이면 **차단 유지**(보류) | 창 상대 캐시가 유효하다고 입증될 때만 shield 유지. 아니면 `UNCERTAIN` | 경로별 `ARMED` 또는 `UNCERTAIN` | `UNCERTAIN`이면 즉시 경고. 침묵 금지 | UIA 실패 주입 시 누출 0 |
| 전경 앱 변경 | 타 앱의 입력을 삼키지 않도록 **즉시 해제** (정당한 해제) | 해제 | 대상이 미지원이면 `OUT_OF_SCOPE` | 보호 범위 이탈 표시 | 전경 전환 n≥300에서 타 앱 입력 삼킴 0, 해제 지연 상한 기록 |
| 컴포저 변경 | 이전 허용 폐기, 새 epoch, 재판정까지 **차단 유지** | 새 epoch까지 `UNCERTAIN` | `UNCERTAIN` → 재판정 후 `ARMED` | 필요 시 | G3-4 |
| Send 버튼 위치 변경 | 영향 없음 | 재배치 확인 전까지 `UNCERTAIN` (**허용 아님**) | 마우스 경로 `UNCERTAIN` | 경고 | 이동·크기·줄 증가 중 누출 0, 불확실 구간 상한 기록 |
| Native shield 생성 실패 | 키보드 경로 단독 주장 금지 | `UNARMED` | 전체 상태 `PARTIAL` | 보호 범위 이탈 경고 | 생성 실패 주입 |
| 핫키 등록 실패 (이미 사용 중 등) | `UNARMED` | 영향 없음 | 해당 경로 `UNARMED` | 보호 범위 이탈 경고 | 선점 상황 주입 |
| 사용자 입력 중 PRIVON 오류 | 해당 입력은 **보류**하고 경고. 반복 오류가 임계값을 넘으면 통제를 해제하되 **경고를 남긴다** (조용한 해제 금지) | 같음 | 오류 중 `UNCERTAIN`, 해제 후 `UNARMED` | 필수 | 예외 주입 |
| PRIVON 비정상 종료 | OS가 소유 자원을 정리해야 한다 (핫키, 창). **미실측** | 같음 | 종료 후 통제 없음 | **경고 불가** (프로세스가 없음). 정적 문서 고지로 대신함 | 강제 종료 후 N초 내 입력 정상화, 잔존 창 0, 5/5 |
| 미지원 앱으로 전환 | 해제 | 해제 | `OUT_OF_SCOPE` | 보호 범위 이탈 표시 | 전경 전환 시험 |

**해제 규칙**: 통제는 (1) 전경 변경으로 대상이 아닐 때, (2) 오류 임계 초과로 명시적 경고와 함께, (3) 사용자가 끌 때만 해제된다. UIA 실패는 해제 사유가 아니다.

## 6. 가장 작은 실험 범위

**단계별로 진행하며, 앞 단계가 합격해야 다음으로 간다.**

| 단계 | 대상 | 목적 | 승인 |
|---|---|---|---|
| X0 | 이 실험을 위해 만든 **격리 테스트 대상 앱** (텍스트 상자 + Send 버튼 + 로컬 전용 수신기, 네트워크 코드 없음, UIA 제공자 켜고 끄기 가능) | 메커니즘 수준에서 G1~G4를 답한다. IME, DPI, 다중 모니터, 강제 종료 정리 포함 | 별도 Controller 승인 |
| X1 | 실제 ChatGPT Windows 앱 한 곳 | X0에서 합격한 조건이 실제 앱에서도 유지되는지 | 별도 승인, 합성 문자열, 별도 계정, 외부 전송 승인이 필요 |
| X2 | Claude Windows, Web, 비한국어 UI | 범위 확장 | 별도 승인 |

X0만으로 제품 보안 기능을 주장할 수 없다. X0는 "메커니즘이 구조적으로 가능한가"에만 답한다.

## 7. 실제 Windows 검증이 필요한 항목

자동화 테스트(가짜 네이티브 이음매)로는 대체할 수 없다.

- `RegisterHotKey`의 숫자패드 Enter, Ctrl+Enter, 키 반복(autorepeat), 한국어 IME 조합 확정 Enter 동작
- 승격된(관리자 권한) 대상 앱에서의 핫키와 shield 동작
- shield의 마우스 차단: DPI 배율, 다중 모니터, 터치/펜 입력, 창 최소화·복원
- 컴포저 포커스 질의와 Send 버튼 탐색의 지연 및 실패 분포 (정상 상태와 부하 상태)
- UIA 컴포저 변경 이벤트의 지연과 누락
- 프로세스 강제 종료 후 핫키·창 정리, 로그오프/잠금/절전 복귀
- 앱 업데이트에 따른 UI 변경 (버튼 이름, 클래스명)
- Windows 버전별 차이 (Windows 10/11)

## 8. 구현 진입 조건과 중단 조건

**진입 조건 (모두 소스와 실측으로 확인되기 전에는 제품 수준 Send Guard를 추가하지 않는다)**

| # | 조건 | 해당 합격 조건 |
|---|---|---|
| 1 | 지원 대상과 입력 경로가 명확하다 | G1-1, G2 경로표 |
| 2 | 통제 경로가 실제 전송 전에 작동한다 | G2-3 |
| 3 | 대상 식별 실패 시 처리 정책이 명확하다 | G1-4, G4 |
| 4 | 미보호 전송을 막는 조건이 입증된다 | G2-1, G3-1, G3-3 |
| 5 | 정상 전송을 안전하게 허용할 방법이 입증된다 | G3-2, G3-4, G3-5, G3-6 |
| 6 | 프로그램 종료 시 원치 않는 입력 차단이 남지 않는다 | G4 비정상 종료 행 |

미충족 시 `A1_FAIL_CLOSED_PROVEN=FALSE`를 유지한다.

**중단 조건 (하나라도 만족하면 Send Guard 개발을 중단하고 Clipboard-first 전용으로 유지한다)**

- G3에 대해 S1과 S2 모두 경쟁(G3-3)을 닫지 못한다.
- R4(마우스)가 UIA 실패 또는 레이아웃 변경 조건에서 누출 0을 만족하지 못하고, 이를 해소할 UIA 비의존 위치 근거도 없다.
- 정상 전송을 위해 무조건 해제가 필요하다 (G3-5 위반).
- 한국어 IME 조합 중 정상 입력을 깨뜨린다 (G3-7 위반).
- R5처럼 소유자가 없는 경로가 남아, Controller가 경로 한정 주장을 승인하지 않는다.
- 비정상 종료 후 입력 차단이 남는다 (진입 조건 6 위반).

## 9. Controller의 다음 실험 승인이 필요한 항목

1. X0 격리 테스트 대상 앱의 제작과 실행 (신규 도구 프로젝트이며 제품 어셈블리가 아님)
2. 실제 Windows 핫키 등록, shield 창 생성, 입력 주입을 포함한 실측 (이 계약의 본문은 실험을 실행하지 않는다)
3. 정상 전송 구조 S1의 입력 재주입, 또는 마우스 경로의 전달 방식, 그리고 README "자동 전송 없음" 문구와의 관계
4. 통계 기준: n≥300 (기능 확인), n≥3000 (출시 게이트) 중 어디까지 요구할지
5. 경로 한정 주장의 허용 여부와 문구 (R5 처리)
6. X1에서 실제 앱에 합성 문자열을 보낼 때의 별도 계정, 데이터 삭제 절차
7. 제품 소스에서 `FocusedElement` 외에 UIA 이벤트를 쓰는 것에 대한 허용 (컴포저 변경 이벤트)

측정 절차는 [send-guard-measurement-protocol.md](send-guard-measurement-protocol.md)를 따른다.
